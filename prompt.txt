The product is NOT:

* a generic AI report generator
* a website SEO auditor
* a competitor scraper
* a chatbot
* a collection of disconnected audits
* an LLM prompt that produces a polished PDF

The product IS:

> An evidence-backed strategic intelligence system that takes an entity, a strategic objective, an audience and a relevant comparison landscape, researches the environment, constructs an evidence graph, identifies findings and opportunities, produces recommendations, and translates those recommendations into an actionable change plan.

# 5. THE EVIDENCE DISCIPLINE

This is one of the most important requirements.

The system must distinguish:

## Observation

Something directly observed.

Example:

"The homepage headline states X."

## Evidence

An observation with provenance that supports a claim.

Example:

"X appears in the homepage hero and About page."

## Interpretation

What the evidence suggests.

Example:

"This positions the entity primarily around technical capability."

## Finding

A meaningful conclusion derived from multiple observations/evidence.

Example:

"Business-outcome differentiation is underdeveloped relative to the comparison set."

## Opportunity

A strategically useful gap or potential advantage.

Example:

"Technology economics is a relatively underoccupied positioning territory."

## Recommendation

What should be done.

Example:

"Reframe the primary proposition around technology outcomes."

## Action

A concrete implementation change.

Example:

"Rewrite homepage hero headline and supporting proposition."

Do not allow the LLM to silently collapse these levels.

---

# 6. EVIDENCE MUST HAVE PROVENANCE

Every evidence item must have:

* unique ID
* source
* source type
* source URL/path/reference where applicable
* observation
* extracted claim if applicable
* date observed
* relevance
* reliability/confidence
* supporting context
* entities involved
* research question(s) supported

Example:

```json
{
  "id": "E-104",
  "source_id": "S-021",
  "source_type": "website",
  "observation": "The homepage headline focuses on technical capability.",
  "claim": "The current positioning emphasises technical capability.",
  "date_observed": "2026-09-07",
  "relevance": "high",
  "reliability": "high",
  "supports": ["F-023"]
}
```

Never fabricate evidence.

Never create a source that was not actually observed.

Never cite an inference as though it were a direct observation.

---

# 15. RESEARCH SHOULD BE ITERATIVE

Do not run one giant research prompt.

Use a loop:

```text
Research Question
↓
Find Sources
↓
Extract Evidence
↓
Assess Coverage
↓
Enough evidence?
├── YES → Analyse
└── NO  → Research again
```

Research should have stopping criteria.

Do not continue researching indefinitely.

Stop when:

* the research question is sufficiently answered
* additional sources are producing diminishing returns
* evidence is sufficiently triangulated
* remaining uncertainty is explicitly recorded

---

# 16. RESEARCH COVERAGE

For every major analytical area, maintain:

* questions asked
* sources found
* evidence collected
* evidence quality
* unanswered questions
* confidence

This enables the final report to say:

> We have high confidence in positioning analysis but insufficient evidence to assess actual conversion performance.

That is preferable to inventing certainty.

# 17. COMPETITIVE / COMPARISON ANALYSIS

This is a core product capability.

Do not model everything as "competitors".

The comparison landscape may contain:

## Direct competitors

Entities pursuing the same audience/objective.

## Indirect competitors

Entities competing for the same decision.

## Alternatives

Different approaches to solving the same problem.

## Substitutes

Different products/services/actions that satisfy the underlying need.

## Benchmarks

Entities that are not competitors but provide useful standards.

## Aspirational comparisons

Entities whose positioning or execution provides useful lessons.

The system should explicitly classify the relationship.

# 30. UNKNOWN / ASSUMPTION MODEL

The system must explicitly maintain:

## Known

Facts supported by evidence.

## Assumptions

Interpretations used because evidence is incomplete.

## Unknowns

Things the research cannot establish.

## Hypotheses

Potential explanations/opportunities requiring validation.

Example:

```text
KNOWN
✓ Public positioning
✓ Published content
✓ Competitor messaging

UNKNOWN
? Actual conversion rate
? Lost opportunities
? Internal perception

HYPOTHESIS
The current positioning may undersell commercial outcomes.
```

Never represent unknowns as facts.

# 43. AGENT ARCHITECTURE

* defined outputs
* validation
* provenance
* error handling at system boundaries

# 44. SUBAGENTS

Use subagents only when work:

* can run independently
* benefits from isolated context
* is genuinely parallel
* has a well-defined output

Do NOT spawn subagents for:

* trivial searches
* simple file edits
* single-file changes
* operations where shared context is essential

Avoid agent proliferation.

The simplest architecture that works is preferred.

# 46. VALIDATION

# 51. IMPORTANT PRODUCT PRINCIPLE: ALWAYS CONSIDER THE OUTSIDE WORLD

A major insight from this project:

> Analysing an entity only against itself is often insufficient.

For example:

"Your homepage could be clearer."

is weak.

Better:

"Your homepage could be clearer, and compared with 11 relevant alternatives, the largest differentiation gap is X."

Therefore competitor/comparison analysis should be an integrated part of onboarding/research, not an optional afterthought.

However:

Do not force competitive analysis when the objective genuinely does not require it.

Use a decision rule based on objective/context.

---

# 52. MARKET RESEARCH AND COMPETITIVE ANALYSIS

Treat these as related but distinct.

## Market research asks:

* What is happening externally?
* What trends matter?
* What audiences exist?
* What needs exist?
* What is changing?
* What opportunities are emerging?

## Competitive analysis asks:

* Who else occupies this space?
* How do they position themselves?
* What alternatives exist?
* What are the norms?
* What is crowded?
* Where is the white space?

Both feed into strategic analysis.

# 53. CONSULTANCY-GRADE OUTPUT STANDARD

The product should behave like a strong strategy/research consultancy.

But do not reproduce consultancy theatre.

Do not produce:

* generic frameworks for their own sake
* arbitrary scores
* filler
* obvious observations
* huge competitor descriptions without synthesis
* recommendations unsupported by evidence
* 100-page reports that say nothing
* unnecessary jargon

The standard is:

> Detailed where detail changes a decision. Concise where it does not.

# 54. SEAMLESS USER EXPERIENCE

The ideal user journey:

```text
1. Tell us what you are trying to achieve.
          ↓
2. Give us your entity/site if relevant.
          ↓
3. Tell us any known comparisons.
          ↓
4. We infer the research context.
          ↓
5. We show our research plan.
          ↓
6. User can correct it.
          ↓
7. Research runs.
          ↓
8. Evidence accumulates.
          ↓
9. Analysis is performed.
          ↓
10. Findings emerge.
          ↓
11. Opportunities emerge.
          ↓

          ↓
13. Changes are mapped.
          ↓

      - executive brief
      - detailed plan
      - interactive HTML
```

The user should not have to understand:

* research methodology
* ontology
* graph theory
* evidence modelling
* agent orchestration
* source classification

Those are implementation details.

# 62. RECOMMENDATION → CHANGE TREE

This relationship must be deterministic wherever possible.

For each recommendation:

```text
affected_assets:
[
  {
    "type": "website_page",
    "path": "/",
    "operation": "edit",
    "target": "hero"
  }
]
```

The renderer can then generate:

```text
WEBSITE/
└── [EDIT] Homepage
    └── [EDIT] Hero
```

This prevents the Change Tree from becoming another hallucination layer.

# 63. OUTPUT TRACEABILITY

Every displayed recommendation should allow the user to answer:

Recommendation
↓

↓

↓

# 64. CONTRADICTIONS

The evidence model must support contradictory evidence.

Example:

Source A:
"Company positions itself as enterprise-first."

Source B:
"Most visible customer examples are SMB."

Do not force a single conclusion.

Represent:

```text
E-001 supports F-001
E-002 contradicts F-001
```

Then analyse the contradiction.

This can itself become a finding.

---

# 65. CONFIDENCE

Use confidence at multiple levels.

## Evidence confidence

How trustworthy is the source/observation?

## Analytical confidence

How strongly does the evidence support the finding?

## Recommendation confidence

How confident are we that the recommended action follows from the analysis?

Do not conflate them.

Use qualitative levels where numerical precision is unjustified:

* High
* Medium
* Low

If numerical values are used internally, do not necessarily expose them publicly.

---

# 66. RESEARCH SOURCE QUALITY

Where relevant, prefer:

1. primary sources
2. official sources
3. direct evidence
4. authoritative third-party sources
5. reputable secondary sources
6. weaker sources only where useful and clearly labelled

Do not treat all sources equally.

---

# 67. RESEARCH CITATIONS

The final report must preserve source provenance.

Every externally derived material claim should be traceable to its source.

Where the output format permits, expose citations inline.

The user should be able to inspect source context.
